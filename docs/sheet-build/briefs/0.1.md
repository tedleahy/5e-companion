### Spelling
- The config is `frontend/cspell.json` and the project word list is `frontend/cspell-words.txt`. `npm run spell` runs it from `frontend/`.
- Frontend scope is everything tracked under `frontend/` except `package-lock.json`, `cspell.json`, `assets/` and generated folders.
- Backend scope is `backend/app/controllers/**`, `backend/app/mailers/**`, `backend/app/models/**`, `backend/app/views/**` and `backend/config/locales/**`. cspell reads whole files, so comments in those files count too.
- `docs/` and `mockups/` are never scanned.
- The word list holds game terms and project names. A real misspelling never goes in it to get a pass.
- Fix every existing typo and British spelling cspell finds in scope, even in a file outside the allowed paths. This is the only exception to the allowed paths, and those edits must be spelling only. The plan lets a step list existing violations instead, but this step can't use that for spelling, because `npm run spell` has to pass.
- Put these fixes in their own commit, `fix: correct existing spelling`, so the reviewer can check that commit changes nothing else.
- Renaming a misspelt identifier means changing every use of it in that commit. If an existing test asserts the misspelt text, correct the test too and say so under "Tests I changed" in the handoff.
- Don't rename a misspelt database column, API field or anything else stored or sent outside the app, because that changes a contract. Stop and raise it under "Questions for you" in the handoff. The step can't merge until it's decided.
- cspell's `flagWords` match exact forms, so list each form you want caught. Start from these: colour, armour, grey, levelling, levelled, honour, favour, favourite, behaviour, neighbour, centre, metre, defence, offence, catalogue, travelling, cancelled, labelled, modelled, organise, recognise, realise, analyse, customise, initialise, normalise, synthesise. Add their plural, `-ed` and `-ing` forms where English has them. Leave out `dialogue`, which is correct American English.

### Lint
- A colour literal is a hex, `rgb()`, `rgba()`, `hsl()` or `hsla()` value anywhere in a string, or a CSS colour name on a colour key or prop. `none`, `transparent` and `url(#id)` are not colour literals.
- "In styles" means `StyleSheet.create`, inline `style` values in every form, including arrays, conditionals and the function form `Pressable` takes, and the JSX props `color`, `fill`, `stroke`, `stopColor`, `tintColor` and `placeholderTextColor`.
- `frontend/src/theme/**` is exempt, because the tokens are defined there.
- `fontWeight` is banned as an object key, a JSX attribute and a member access. Comments and other strings may mention it.
- Both rules are errors, not warnings, because `expo lint` exits 0 on warnings.

### Routes check
- `node scripts/check-routes.js [dir]`, run from `frontend/`, checks `dir` and defaults to `src/app`. On a violation it prints each offending path and exits non-zero. `npm run check:routes` runs it with no argument.
- A route is a `.js`, `.jsx`, `.ts` or `.tsx` file, including `.web`, `.native`, `.ios` and `.android` variants, with a default export. `export default`, `export { x as default }` and `export { default } from` all count.
- `+api` and `+native-intent` files use named exports, so they skip the default export check.
- Groups such as `(tabs)/` and dynamic files such as `[id].tsx` and `[...rest].tsx` pass.
- The script fails on test and spec files, on `__tests__`, `__mocks__` and `__snapshots__` folders, on any other extension, and on a source file with no default export.
- It can't tell a helper component with a default export from a screen. That limit is accepted.

## Tests already written
None at the time of writing. The test writer adds the files below before the implementer starts, and they fail until the step is built. Step 0.2b builds the script that normally commits them, so this time they're committed by hand.

Once they exist, don't edit them. If one is wrong, say so in the handoff.

The tests are JavaScript because they use Node built-ins and `tsconfig.json`'s `types` array loads only `jest`.

- `frontend/scripts/spelling.test.js` runs cspell with the real config, through stdin or a temporary file. It fails on a flagged word in camelCase (`inkColour`), in snake_case, in upper case (`GREY`) and in a copy string, and on an unknown word. It passes American spellings and a game term from the word list, such as `cantrip`. It also proves a file in the backend scope is checked and a file under `docs/` isn't.
- `frontend/scripts/style-rules.test.js` runs ESLint with the real `eslint.config.js`, so it proves the rules are switched on as well as correct. Bad examples cover a hex, an `rgba()` and a colour name, each in `StyleSheet.create`, an inline style and a JSX colour prop, and `fontWeight` as a key, a JSX attribute and a member access. Good examples cover a theme token, `fill="none"`, `fill={`url(#${id})`}`, `pointerEvents: 'none'`, a raw colour in a file under `src/theme/`, and a comment that mentions `fontWeight`.
- `frontend/scripts/check-routes.test.js` builds temporary directories and runs the script against them. It covers each failing and passing case listed under "Routes check", and the default `src/app` passing on the current code.
- `frontend/scripts/check-script.test.js` reads `package.json` and asserts that `check` includes the format check, lint, typecheck, tests, `spell` and `check:routes`.

## Known pitfalls
The log has no entries yet, because this is the first step. These come from reading the current code.

- `frontend/src/theme/colors.ts` is full of raw colours on purpose. It needs the exemption above.
- `frontend/src/theme/index.ts:17` mentions `fontWeight` in a comment, so a text search would report a false failure. Match on the syntax tree.
- `fill="none"` appears in four components, and `frontend/src/components/paper.tsx` uses `fill={`url(#${id})`}`. A loose hex pattern would flag the second.
- The only British spelling I found in scope is the comment at `backend/app/models/character.rb:1`. cspell may find real typos elsewhere, and "Spelling" says what to do with them.
- I found no existing lint or routes violations. If one turns up outside the allowed paths, the spelling exception doesn't cover it, so stop and raise it under "Questions for you" in the handoff.
- Bad examples must not fail the real checks. Test files that contain flagged words need `cspell:disable-next-line` or a word built at runtime. Never create a bad example under `frontend/src/app/`, because every file there becomes a route.
- A test that spawns `npm run check` or `npm test` runs Jest inside Jest and never ends. `check-script.test.js` reads `package.json` for this reason.
- cspell resolves globs from its root, so reaching `../backend` from `frontend/` needs `globRoot` or `--root`. Confirm the backend files are actually checked. A wrong glob passes silently.
- A new worktree has no `node_modules`. Run `env mise exec -- npm ci` in `frontend/` before anything else.
- cspell is a JavaScript-only dev dependency, so it doesn't affect Expo Go.
