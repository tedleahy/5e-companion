## Findings

### 1. must-fix: valid RGB forms still bypass the rule in rendered web styles

Location: `frontend/eslint-rules/no-color-literals.js:163-178`.

The number pattern omits scientific notation, and the function patterns require numeric channels. With the real ESLint config, all three of these inputs produce zero errors:

```tsx
<View style={{ boxShadow: '0 2px 4px rgb(1e2 0 0)' }} />
<View style={{ boxShadow: '0 2px 4px rgb(none 0 0)' }} />
<View style={{ boxShadow: '0 2px 4px rgb(from red r g b)' }} />
```

I reproduced the lint results with a real `View` import and the virtual filename `src/components/review-probe.tsx`. I also rendered each style through the installed `react-native-web` and `react-dom/server`. Each value survives unchanged in the resulting `box-shadow` attribute.

I then assigned the resulting shadow strings to elements in local headless Chromium. `CSS.supports('box-shadow', value)` returned `true` for all three. `getComputedStyle(element).boxShadow` returned, in the same order:

```text
rgb(100, 0, 0) 0px 2px 4px 0px
color(srgb none 0 0) 0px 2px 4px 0px
color(srgb 1 0 0) 0px 2px 4px 0px
```

These are concrete rendered raw colors in a style string. The brief requires RGB literals anywhere in such strings to fail, and does not limit that rule to the native color normalizer's accepted syntax. The exemptions for a standalone `none`, `transparent`, and a paint URL do not exempt an RGB function containing a `none` channel.

Reject these function forms while preserving the documented theme and paint URL exemptions. Recognizing only selected numeric function arguments leaves the check incomplete.
