## Findings

### 1. must-fix: valid RGB and HSL literals bypass the color rule

Location: `frontend/eslint-rules/no-color-literals.js:161-164`.

The RGB and HSL patterns recognize only some valid function forms. With the real ESLint config, each of these inline styles produces zero errors:

```tsx
<View style={{ color: 'rgb(255, 0, 0 )' }} />
<View style={{ color: 'rgb(255 0 0)' }} />
<View style={{ color: 'rgba(255 0 0 / 0.5)' }} />
<View style={{ color: 'hsl(-30, 100%, 50%)' }} />
```

I reproduced all four using `ESLint.lintText` with `src/components/review-probe.tsx` as a virtual filename and a real `View` import. The installed `@react-native/normalize-colors` accepts all four, returning `4278190335`, `4278190335`, `4278190208`, and `4278223103`, respectively. These are valid rendered colors, so the missing diagnostics allow raw colors through the check later steps rely on. The brief requires RGB, RGBA, HSL, and HSLA literals to fail, without restricting their whitespace, separators, or hue sign.

Recognize the valid function syntax, including whitespace before the closing parenthesis, space-separated channels, slash alpha, and signed hue. Keep the existing theme exemption and paint URL exception.

### 2. must-fix: static template keys and member accesses bypass the rules

Locations: `frontend/eslint-rules/no-font-weight.js:39-58` and `frontend/eslint-rules/no-color-literals.js:297-301`.

The font rule skips every computed key or member that is not an ESTree `Literal`. An expression-free template is a `TemplateLiteral`, even though its value is statically known. These both produce zero errors with the real config:

```ts
export const styles = { [`fontWeight`]: 700 };
export const weight = (style) => style[`fontWeight`];
```

Both use the exact banned property. The color rule has the same omission when reading property names:

```tsx
<View style={{ [`color`]: 'red' }} />
```

I reproduced zero errors for that example too, with the `View` import. At runtime its key is `color`, so it renders the forbidden named color. This violates the brief's bans on `fontWeight` object keys and member accesses and on CSS color names at color keys. It needs no variable evaluation to detect.

Handle expression-free template literals when resolving static keys and member names. A dynamically computed property whose value is unknown can remain outside this static check.
