Ground rules

These apply to every step in every milestone. Each step brief repeats the ones that matter for it, because an implementer may not read this page.

Current state, 20 October 2026

  • The character list is built and merged. GET /api/v1/characters is the only endpoint.
  • The backend has five of the data model's eleven character tables, several of them with fewer columns than data-model.md lists, and no catalog tables. Nothing from srd-json-files is imported, and nothing derives sheet values yet.
  • The mockup has 58 phone frames, numbered in the order of character-sheet-plan.md's list, plus desktop and tablet frames counted separately as d1, t1 and so on. It has no loading, error or not-found frames for the sheet.
  • The design system took in the sheet's components in v0.4. Its frames are the reference for every primitive.

Rules for every step

  • Follow AGENTS.md. The front-end rules that come up most: React Native primitives styled with @/theme, no raw hex in styles, weight through fontFamily, useBreakpoint() for width-dependent layout, nothing but routes in src/app/, JSDoc and YARD as AGENTS.md describes, blank lines between adjacent test assertions.
  • UI copy is American English, sentence case, second person for the player and third person for the character, with no pronouns for the character because the data model stores none. This plan and the design system stay in British English.
  • Run tools through env mise exec --. Finish with bin/check-step once milestone 0 has built it. Until then, the front-end checks AGENTS.md lists and backend/bin/ci.
  • Stay inside the step's allowed paths. If the step needs something from a later step, stop and say so in the handoff brief instead of building it.
  • Write the least code that meets the brief and passes its tests. Handle only what the app can produce or someone could plausibly write. Add no option, abstraction, guard or fallback that nothing in the brief needs.
  • Test writers write one test per behaviour the brief names. Skip variations of the same behaviour and inputs the app can't produce.
  • When fixing a review finding, prefer a fix that replaces code over one that adds to it.
  • Brief writers and implementers commit to their own step branch, as conventional commits, because the brief asks them to. Nobody commits to the milestone branch or main except by merging an approved step.

Branches

  • Each milestone has a branch off main, such as feature/sheet-m1.
  • Each step has a branch off the milestone branch, such as sheet-m1/f4-play-tab, in its own worktree, with a pull request back into the milestone branch.
  • An approved step merges into the milestone branch. Steps that were built in parallel rebase onto it before their own review if the branch moved.
  • The milestone branch merges into main once its definition of done is met.

Agent workflow

The loop each step goes through before it reaches you, and who does what. The point is that only judgment calls are left by the time you review.

Roles

A step's lifecycle

  1. BriefA short Opus 5.5 session writes the step's brief from the template and exits.
  2. Tests firstThe test writer writes failing tests. The script confirms they fail and commits them.
  3. BuildThe implementer works until the tests and bin/check-step pass.
  4. Checksbin/step-next reruns bin/check-step and retakes the screenshots.
  5. ReviewA fresh reviewer per round, with the screenshots on UI steps. Must-fix findings go back to step 3.
  6. HandoffThe brief, the review log, the comparison page and your questions.
  7. YouApprove and merge, or send back with notes.

Rules for the loop

  • Tests come from Sol, never the implementer. An implementer writing its own tests tends to make them match its bugs. The test writer locks the expected behaviour first. Sol also reviews the step, so you're the only second opinion on its tests. Your review starts with them, and they say what the step is meant to do in fewer lines than the code.
  • Briefs are self-contained. A brief carries only what the step needs: the frames, the design system sections, the fixture paths, the allowed paths, the decisions that apply, and known pitfalls. Less to read makes a cheaper model more accurate and costs fewer tokens.
  • Scope is enforced mechanically. bin/check-step fails when git diff --name-only against the milestone branch leaves the brief's allowed paths. Shared files, such as the theme, the component index and the routes, change only in steps that list them.
  • Findings carry a severity. must-fix goes back to the implementer. should-fix and nit are batched into the handoff for you to decide. question goes straight to you. Every finding needs a concrete failure scenario, and the reviewer reproduces it where it can. Differences from the frames are listed separately with no severity, and the latest round's list comes to you.
  • Two rounds, then escalate. If the second review still has must-fix findings, or the implementer reports it's stuck, the step goes to Opus 5.5, not a third Grok round. A step Opus 5.5 is already implementing comes to you instead. The log records every escalation, which shows where Grok is worth using.
  • Nothing takes an agent's word for it. bin/step-next reruns the checks rather than accepting a "done", and offers no review until they pass. The Claude Code Stop hook from step 0.2a only binds agents running in Claude Code, so for Grok and Sol this run is the gate.
  • A script takes the screenshots, not an agent. Before each review round, bin/step-next retakes them from the committed branch, so a review never sees stale shots or the wrong state. Every round reads them, because nobody knows which round is the last. An implementer can run the script while building, but the retake replaces its shots. A step with no frames in frames.json skips this.
  • At most two steps wait for you. No new implementer starts while two steps sit in your queue, even when the plan allows parallel work. Otherwise output piles up and branches go stale.
  • State lives in files. Briefs, review rounds and the log live under docs/sheet-build/ on the step branch, so a fresh session can pick up where the last one stopped.
  • Your misses feed the loop. Every finding you make that the reviewer missed goes in the log, and becomes a line on the review checklist, a known pitfall in later briefs, or a lint rule. Something you've flagged twice is never left to review a third time.

Choosing the implementer

Each step below carries a suggested implementer. Grok 4.7 where the target is checkable: a primitive with a frame, a tab that renders a fixture, a migration from a written spec, an endpoint that must equal a golden file. Opus 5.5 where the step is mostly judgment: rules derivation, web and native accessibility, layout plumbing, and later the optimistic updates. You marks a step that needs your decisions more than code. Parallel marks steps that can run at the same time, within the queue limit.

Try it on milestone 0 first

Milestone 0 is well specified and low risk. Run it with Grok implementing, and track rounds, escalations, your review time and usage per step in the log. Then decide whether Grok is worth it for milestone 1's frontend steps, and whether any subscription needs upgrading.

Working within the limits

Every limit figure we could find is approximate, and many come from third-party guides. Go by /usage in Claude Code, Codex's usage settings and the Spending tab of Cursor's dashboard.

  • Claude sessions stay short. A long session rereads its whole context on every call, and Claude is likely the tightest limit. This plan's own thread averaged about 165,000 tokens a call. So no Opus session outlives its brief or its step.
  • Stopping is routine. A limit can cut an agent off without warning, so implementers commit each time another test passes. The next session reads the last commit and anything uncommitted, then keeps or discards that work, and the log records the stop. Tests and reviews never fall to the step's implementer to save waiting.
  • Stops don't count as rounds. Rounds are counted from finished review files, so a review cut off partway runs again without counting, and so does a resumed implementer session. A usage limit can't trigger an escalation by accident.
  • If Codex runs out. On a Grok step, you can have Opus 5.5 write the tests or do the review so the work keeps moving, and the log notes the switch. On an Opus 5.5 step, tests and reviews wait for Sol.
  • Usage is measured on milestone 0. The script records each run's token counts where the tool reports them. When a step reaches you, read the percentage used of each subscription's 5-hour window and weekly limit, or Cursor's models pool, and add it to the step's log. A milestone 1 step that wouldn't fit in one window on those numbers gets split before it starts.
  • Grok 4.7 draws from Cursor's own models pool. Cursor's docs confirm this, so it doesn't use the third-party allowance. The pool on your plan is monthly, and extra usage doesn't bill automatically, so running out stops Grok rather than charging you. Cursor publishes no size for the pool, so milestone 0 measures it. Its four Grok steps are the basis for projecting milestone 1's twelve.
  • If Grok runs out. A monthly pool could mean weeks of waiting. Either Opus 5.5 takes the remaining Grok steps from the existing tests and work so far, or you turn on extra Cursor usage, whichever milestone 0's numbers make cheaper. Sol's reviews stay independent either way.
  • A timer runs the loop. From step 0.3 on, bin/step-next --run starts agents through claude -p, codex exec and cursor-agent -p, and a timer calls it every 30 to 60 minutes. It uses no model of its own, and it notifies you when a step is waiting on you or stuck. If it's stuck, one short Opus 5.5 session diagnoses it, which costs far less than an Opus orchestrator because it only runs on steps that fail. If Claude is at a limit too, you get the notification without the diagnosis. Switching a step's model after a long stop stays your call. Before step 0.3, check that each provider's terms allow unattended use. Where they don't, that agent runs by hand.

If Claude is what runs out

Move to the £100 Claude plan for the month you build milestone 1. Third-party guides put it at about five times Pro's usage per 5-hour window, though the weekly limit still applies and we couldn't find how much it grows. Opus 5.5 can then write the tests on steps Grok implements, which takes load off Codex.

Short sessions, the split steps, frequent commits and the usage log all stay. Upgrading Claude doesn't help if Codex or Cursor runs out first.

Review checklist, seeded from the character list

Each line is a finding from the list's review that a reviewer has to look for because no check catches it yet.

  • Headings have levels on the web, and the web gets the same accessible names as native.
  • Every control has a role, a name, and the state the sheet plan's ARIA decisions give it: tabs with aria-selected, single choices as radios, toggles with aria-pressed, disclosures with aria-expanded, pip rows as one adjustable control.
  • Every control answers across at least 44 by 44, with neighbouring areas meeting at the midpoint.
  • Focus survives a remount: a breakpoint change or a retry doesn't drop keyboard focus.
  • Offline, a missing EXPO_PUBLIC_ setting and a 401 each show their own message, not a generic failure.
  • Limits are counted the way the API counts them, in code points, not UTF-16 units.
  • UI copy uses curly quotes where it quotes, American spelling, sentence case and no pronouns.
  • No number on screen is calculated in the app when the API sends it.

0Milestone 0: review tooling

Build the checks before the code they check. Each step here is small, and the whole milestone doubles as the trial run for the agent workflow.

0.1 Spelling and style rules Grok 4.7

  • cspell on the frontend and the backend's user-facing strings, with an en-US dictionary, a project word list for game terms, and a flagged list of British spellings (colour, armour, levelling, grey and so on) that fails in code and copy. Plans and the design system are excluded.
  • ESLint: no colour literals in styles, no fontWeight anywhere.
  • A script that fails when src/app/ holds anything but routes.
  • npm run check runs format check, lint, typecheck, tests, spelling and the routes check.
  • Each rule has a test that proves it fails on a bad example.

0.2a One entry point, scope and the Stop hook Grok 4.7

  • bin/check-step <id> at the repository root runs npm run check, backend/bin/ci when the diff touches backend/, and the scope check against the brief's allowed block. It prints the diff's size against the milestone branch, not counting tests, beside the brief's expected size. --quick skips the slow parts for use while iterating.
  • A Claude Code Stop hook in the committed .claude/settings.json runs bin/check-step --quick, but only in a worktree that holds a .sheet-step marker file, so ordinary sessions aren't affected. It blocks each stop only once, so a check that keeps failing can't keep an unattended agent running.
  • docs/sheet-build/ with the templates above, a log/ folder with one file per step, so step branches don't conflict over a shared log, and the review checklist.

0.2b The next-step script Grok 4.7

  • bin/step-next <id> reads the step's files and branch, reruns bin/check-step when a review would come next, and prints the next agent, its model and its prompt filled in from the templates. After a second round with must-fix findings, it offers the escalation.
  • Once the test writer has finished, it confirms the new tests fail, then commits them. That commit marks where the tests were finished, and it flags any later edit to those files.
  • The reviewer runs as codex exec -s read-only -o <file>, so Sol stays read-only and the review file appears only if the round finished. The script commits that file.

0.2c Unattended running Opus 5.5

This goes to Opus 5.5 because it runs unattended, and a bug here could waste a lot of usage. Steps up to and including this one run by hand.

  • Before building it, run one small prompt through each of the three tools from a timer. On 8 November, cursor-agent models reported that authentication was required from an agent's shell, even though cursor-agent status said it was logged in.
  • bin/step-next --run also starts the next agent, confined to the step's worktree, one at a time, and a timer calls it. It runs bin/setup in each new worktree, and every agent run has a time limit.
  • It stops at an approval, a question or a full queue, and notifies you. An attempt that exits at once costs nothing, usually because a limit is still in force, so it's retried on the next tick. An attempt that runs and ends with no new commit counts as failed, and three of those on a step stop the timer. So does a day with no progress, which usually means a weekly or monthly limit.
  • Each agent's output goes in the git-ignored docs/sheet-build/runs/<id>/. When failed attempts stop the timer, --run starts one Opus 5.5 session, which reads that output and the branch and writes docs/sheet-build/diagnoses/<id>.md.

0.3 The comparison page Grok 4.7

  • A script that pairs app screenshots with mockup frames from a mapping file, docs/sheet-build/frames.json: route, fixture or seeded character, viewport, and the frame it should match.
  • It renders both sides with the existing shoot.sh scripts and writes one dark page: each pair side by side at the same scale, with a toggle that overlays them and an opacity slider.
  • bin/step-next runs it before each review round on a step with frames. The page and its images go in the git-ignored docs/sheet-build/comparison/<id>/, marked with the commit they came from. A step's handoff links the page.
  • A trial of who reads the images: make a copy of the character list's screenshots with a missing element, wrong copy and wrong spacing added, and run Sol and Grok on it. Log what each one catches. Sol does it as part of the review. Grok would be a separate run, if Cursor passes it images at all. If neither catches enough, you're left with the comparison page and no agent reads the images.

0.4 Accessibility and hit-area checks Opus 5.5

  • A script that loads routes from the web build in headless Chromium over DevTools, injects axe-core (a JavaScript-only dev dependency), and fails on violations.
  • A hit-area check over the same pages: every element with an interactive role answers across 44 by 44, or carries a declared hit slop that makes it so, and no two areas overlap.
  • Confirm first how hit slop reaches the DOM on the web. If react-native-web drops it, the shared pressable exposes it as a data attribute for the check to read. This is why the step goes to Opus 5.5.

Done when

  • The comparison page works for the character list against its mockup.
  • The log has an entry for each step, with its usage.
  • bin/step-next --run has resumed a step after its agent was killed partway, and stopped on a step made to keep failing.
  • You've decided on Grok for milestone 1, on who reads the screenshots, and on whether to upgrade a subscription.

The contract

The draft types are in character-sheet-contract/character-sheet.ts, with a JSDoc line on every field. This section explains the shape; the file is the reference.

Principles

  • Conventions match the list: snake_case keys, ids as strings, every key present, null for none.
  • Lists arrive in display order. The app groups, but never sorts.
  • Facts plus display lines, as decided above. A display line is written for the place it appears, so the same fact can have two lines, such as a resource's summary on Play and a casting card's row built by the app.
  • A value the player can replace is a DerivedValue: value, calculated and override. The override badge shows whenever override isn't null.
  • Lean for milestone 1, additive afterwards.

The golden test

The Rails request test fetches each seeded character and compares the body with its fixture after normalising both:

  • Every string under a key named id, ending in _id, or inside an array under a key ending in _ids, becomes a placeholder numbered by first appearance. Fixture ids can stay readable, like brenna-res-pact, and references still have to point at the right thing.
  • lock_version only has to be a non-negative integer.
  • Everything else, order included, must match exactly.

Jest uses the same files, without normalising, to render each tab. Step 1.1 moves the fixtures to contracts/character-sheet/ so both sides read one copy.

Rules the fixtures follow

The mockup was drawn by hand, so some blocks have no rule behind them. The backend needs one it can apply to any character. Agreed on 24 October; changing one changes the fixtures.

TopicRule
Attack tableManual attack actions first, because the player added them on purpose. Then every weapon the character has outside a container, equipped first, in item order. Then cantrips that make an attack roll or force a save and deal damage. Then levelled spells that keep attacking after the turn they're cast, by level and then name: Spiritual weapon, Flaming sphere, Moonbeam, Heat metal and Arcane sword in the SRD. The summary manifest flags these with attacks_after_casting on Spells, because the SRD data can't pick them out. A spell needs a path that can cast it now, prepared or always prepared. Its damage is at the level that path casts it: a fixed level, the Pact magic level, or else the spell's own level. A row cast above the spell's own level says so in its summary, such as at 3rd. Every other levelled spell stays on the Spells tab.
ActionsGrouped as action, bonus action, reaction and no action needed. Within Action: the Attack row when the character makes more than one attack per Attack action, then spells, then Cast a spell when the character has a levelled spell, then features, then Common actions. A spell gets a row only when one of its paths has its own uses, like Brenna's Cure wounds, or when it's the spell being concentrated on and its rules give it a recurring action, like Hex. Features get a row when the summary manifest gives them an action type. Opportunity attack names the first melee attack.
Attack linesThe app writes the line under an attack's name: what the attack takes when it isn't an action, then the thrown range if there is one, such as 20/60 ft thrown, or else the melee reach, such as Melee, 5 ft, or the range. Then the properties that change the roll, such as finesse and versatile, and then the API's summary. Light and thrown don't show, because the range already says thrown.
Spell orderBy level, then always-prepared spells, then by name.
Spell summaryCasting time and range, then the first of: concentration, the save with its DC, the healing dice, the duration unless instantaneous. A spell that deals damage skips the duration and ends with its damage dice and type, at the level the attack table rule gives, such as Action, 150 ft, Dex save 15, 8d6 fire. Beam and ray handlers write the damage part themselves, such as two beams, 1d10+4 force each. Damage another attack carries, such as Hex's, isn't the spell's own and stays out. A spell with several paths at different levels says which path casts at which level.
Resource orderSlots or Pact magic, then class and subclass feature resources in feature order, then hit dice, then everything else in the order it was added.
Feature groupsClass, subclass, race with its subrace, background, each feat with the level it was taken at, then anything added by hand.
Item linesWeapons: damage, then properties, such as 1d4 piercing, finesse, light, thrown 20/60 ft. Armour: category, AC and any Strength minimum, such as Heavy armor, AC 16, Strength 13. Shields: +2 AC. Containers: how many things are inside. Everything else: the summary manifest, or the grant it came with, such as From the Acolyte background.
Hit dicereset_on is long_rest, because a long rest recovers half. Some current seeds say short_rest.
SummariesStatic lines come from a maintained manifest keyed by catalog type and key, like the correction manifest. Lines that depend on the character, such as Heal 1d10+8 or Two 3rd-level slots, come from rule handlers.

If agents build tabs in parallel before the primitives exist, each invents its own stat tile and pip row, and review time goes on merging them. The tab steps' allowed paths exclude src/components/, so a tab that needs a new primitive stops and asks.
