The current stage stacks three dense editors (multiclass prerequisites, starting proficiencies, multiclass proficiencies), each split into an "Always granted" chip list and one or more numbered "Choice groups". It's functional but jargon-heavy and hard to scan. Below is the baseline plus three redesign directions. Use the switcher to compare.

Baseline — pain points

Developer jargon leaks to users
Choice group 1, "Always granted", "pick N options" describe the data model, not the player's intent ("choose 2 skills").
Three near-identical editors stack vertically
Starting and Multiclass grants look the same and sit far apart — easy to edit the wrong one, and a lot of scrolling on a phone.
Hidden "tap to remove"
Selected chips are removed by tapping, explained only by helper text. No affordance (×) and it clashes with selectable filter chips elsewhere in the app.
Abstract prerequisite logic
"Same group = OR, different groups = AND" asks the user to think like a boolean expression parser.
No result preview
Nothing shows how the finished grant reads on a character sheet.
Reads like the rulebook
The grant is a fill-in-the-blank sentence. Underlined slots are editable; the whole thing mirrors SRD phrasing ("proficient with… and chooses 2 from…").
Fixed & choice unified
No separate "Always granted" vs "Choice groups" sections — a fixed grant is just a slot without a count; a choice adds the chooses N clause inline.
Tabs replace the tall stack
Starting / Multiclass / Prereqs become tabs, killing the scroll and the "edited the wrong block" trap.
Trade-off
Sentence wrapping can get busy with many options; needs care for long tool/weapon names and RTL/accessibility.
One home per proficiency type
Armor / Weapons / Tools / Skills accordions. Users think "what armor?" not "is this fixed or a choice?".
Fixed↔choice is a single switch
"Player chooses a subset" toggle converts a granted list into a pick-N choice in place — no separate add-choice-group flow.
Scannable collapsed state
Each header summarises itself ("Choose 2 of 5", "Simple granted"), so the whole stage fits without opening anything.
Trade-off
"Other" proficiencies that don't fit a type need a catch-all bucket; multiple independent choices within one type (rare) need an "add another choice" affordance.
Preview pinned at the top
A live "what players will see" card keeps the outcome visible while editing — the missing feedback loop from the baseline.
Colour-coded intent
Gold = always granted, claret = player picks. The distinction is visual, not a section heading you have to read.
Explicit remove affordance
Chips carry an ×; the count stepper is embedded in a plain-language callout ("Player chooses 2 of the 5 skills below").
Closest to current architecture
Keeps the fixed-list + choice-group data model intact, so it's the lowest-risk to ship — mostly presentation changes.
Recommendation
Ship C first (low risk, adds preview + clarity), then consider B's per-type toggle to remove the fixed/choice split entirely.
